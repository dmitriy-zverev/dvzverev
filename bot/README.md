# Автопостер Telegram → ВК «Что почитать вайбкодерам»

Серверный бот в текущем репозитории. Публикует готовые посты из JSON-очереди по
расписанию: сначала в Telegram, затем в ВК. Источник — ручная JSON-очередь или
генерация через OpenRouter. Дополнительных npm-зависимостей нет.
Приложение работает отдельно от статического Astro-сайта.

Production на cloudru: [эксплуатация и откат](../deploy/POSTER.md),
[результаты ревью](RELIABILITY_REVIEW.md). Текущий production ведёт три
VK-сообщества и использует Telegram только для уведомлений владельцу.
Третий проект — [«Вещи — кстати»](THINGS.md): редакционные lifestyle-посты,
утром текст, вечером GIF, без товарных ссылок до подключения источника товаров.

Новые планы: [недельный кабинет, Telegram-сводки, аналитика 30 дней и редакционный цикл](../docs/bot-plans/README.md).

## Локальный кабинет `/bot/`

Без деплоя на cloudru:

```bash
# в bot/.env: BOT_CABINET_ENABLED=true, BOT_CABINET_PASSWORD=…, BOT_CONFIG_PATH=bot/service.json
pnpm cabinet:migrate   # SQLite + импорт state
pnpm cabinet:api       # API 127.0.0.1:8787

# в другом терминале
PUBLIC_BOT_API_BASE=http://127.0.0.1:8787 pnpm dev
# открыть http://127.0.0.1:4321/bot/ (тот же host, что API — иначе cookie не уйдёт с localhost на 127.0.0.1)
```

Планировщик для локальной проверки — только dry-run:

```bash
node --env-file=bot/.env bot/run.mjs --dry-run --once
# или цикл без отправок, если в .env нет рабочих VK-токенов
```

Кабинет читает SQLite; бот при `BOT_CABINET_ENABLED=true` синхронизирует state после каждого сохранения.

Защита от перебора пароля: в API считаются **неудачные** попытки входа с IP (`BOT_CABINET_LOGIN_MAX_ATTEMPTS` за окно `BOT_CABINET_LOGIN_WINDOW_SEC`), затем блокировка на `BOT_CABINET_LOGIN_LOCKOUT_SEC` с экспоненциальным увеличением при повторных блокировках. Ответ `429` с заголовком `Retry-After`. Неудачи пишутся в `audit_log` и в stderr как `cabinet_auth_fail ip=…` (для fail2ban). Пока IP заблокирован, scrypt не вызывается.

**Смена пароля:** после первого запуска в SQLite сохраняется `password_hash`; одного изменения `BOT_CABINET_PASSWORD` в `.env` недостаточно — задайте новый `BOT_CABINET_PASSWORD_HASH` (scrypt) или удалите ключ `password_hash` в `cabinet_meta` и перезапустите API. При смене hash через env все сессии сбрасываются.

Пример jail на хосте с systemd/journal (фильтр stderr процесса `cabinet:api`):

```ini
[cabinet-auth]
enabled = true
filter = cabinet-auth
port = http,https
logpath = /var/log/journal/*/system.journal
backend = systemd
journalmatch = _SYSTEMD_UNIT=your-cabinet.service
maxretry = 10
findtime = 600
bantime = 3600
```

`filter.d/cabinet-auth.conf`:

```ini
[Definition]
failregex = ^cabinet_auth_fail ip=<ADDR>
ignoreregex =
```

Если перед кабинетом nginx — можно банить по `POST /bot/api/v1/auth/login` с кодом 401/429 в access log (отдельный `limit_req` не заменяет in-app lockout при прямом доступе к `:8787`).


Для запуска без Docker нужны Node.js >= 22.12 и Python 3 (системная файловая блокировка). Создай бота в [BotFather](https://t.me/BotFather), добавь
его администратором канала с правом публикации. Токен запиши в `bot/.env` на машине,
где будет работать бот. Не добавляй токен в исходники или публичные переменные Astro.

Из корня репозитория:

```sh
cp bot/.env.example bot/.env
chmod 600 bot/.env
mkdir -p bot/content
cp bot/posts.example.json bot/content/posts.json
```

В `bot/.env` заполни `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`. Для публичного канала
можно использовать `@channel_username`; для приватного — числовой ID канала.
Файлы `.env`, `bot/content/posts.json` и `bot/data/` исключены из Git.

Для ВК задай `VK_ACCESS_TOKEN` (ключ сообщества с правом `wall`) и положительный
`VK_GROUP_ID=242034586`. Оба поля обязательны для включения ВК; если оба пусты,
публикация работает только в Telegram. `BOT_ALERT_CHAT_ID` — отдельный Telegram-чат
для всех ошибок обеих площадок.

## Очередь постов

`bot/content/posts.json` — массив публикаций в порядке отправки. Пример структуры ниже —
демонстрационный, замените ссылку и текст реальным материалом перед запуском:

```json
[
  {
    "id": "review-001",
    "title": "Как проверять код, написанный агентом",
    "summary": "Короткая аннотация прочитанной статьи: о чём она и что в ней полезного.",
    "why": "Поможет проверить результат перед деплоем.",
    "action": "Выбрать один критичный сценарий и написать для него тест.",
    "url": "https://example.com/replace-with-real-article"
  }
]
```

`action` необязателен, остальные поля обязательны. `id` должен быть уникальным и
оставаться неизменным после публикации. Новые посты дописывай в очередь; отправленные
можно удалять из очереди, но историю состояния нужно сохранять. Бот перечитывает
очередь перед каждой публикацией. Обновляй её атомарно: сохрани новый JSON во
временный файл рядом, затем переименуй в `posts.json`.

Бот экранирует HTML и оформляет заголовок, аннотацию, пользу и ссылку. Слишком длинный или некорректный пост блокируется до ручного исправления. Невалидная очередь приостанавливает публикации до исправления и команды `--resume`. Пустая очередь
пропускает выпуск без генерации заглушек.

## Запуск

```sh
# Предпросмотр следующего поста: без сетевых запросов и записи состояния.
node --env-file=bot/.env bot/run.mjs --dry-run

# Постоянная работа по расписанию.
node --env-file=bot/.env bot/run.mjs

# Проверить текущий слот расписания один раз (для внешнего планировщика).
node --env-file=bot/.env bot/run.mjs --once

# Немедленно опубликовать следующий пост, независимо от расписания.
node --env-file=bot/.env bot/run.mjs --publish-next
```

Также доступны `pnpm bot:preview`, `pnpm bot`, `pnpm bot:publish`, `pnpm bot:test`.
Публикация настоящая: для первого запуска используй тестовый канал.

Расписание по умолчанию — ежедневно в 10:00 по Москве. Например, два выпуска:

```dotenv
BOT_TIMES=10:00,18:00
BOT_TIMEZONE=Europe/Moscow
```

Время задаётся в формате `HH:mm`. Процесс проверяет расписание каждые 15 секунд,
в течение пяти минут после указанного времени; старые пропущенные выпуски не
догоняет. Повторная проверка того же слота не отправляет второй пост. Если в текущий
слот очередь была пустой следующий автоматический выпуск произойдёт в следующий слот. Временный отказ Telegram запускает отдельный повтор с задержкой, в том числе вне слота расписания. Ручная публикация не отменяет будущий слот.

## Локальный запуск в Docker

Docker Desktop должен работать; компьютер должен оставаться включённым и не уходить
в сон к моменту публикации. Docker-образ содержит только код бота. Ключи подключаются
из `bot/.env` при запуске; очередь и история сохраняются в локальных каталогах
`bot/content/` и `bot/data/` вне контейнера.

Из корня репозитория:

```sh
mkdir -p bot/content bot/data
# Только при первой настройке, если очередь ещё не создана:
cp -n bot/posts.example.json bot/content/posts.json

# Сборка и запуск в фоне.
docker compose -f bot/compose.yaml up -d --build

# Статус и журнал.
docker compose -f bot/compose.yaml ps
docker compose -f bot/compose.yaml logs --tail 100

# Проверка токена, канала и права публикации — без отправки сообщений.
docker compose -f bot/compose.yaml exec poster node bot/check-telegram.mjs

# Предпросмотр следующего поста.
docker compose -f bot/compose.yaml exec poster node bot/run.mjs --dry-run

# Немедленно опубликовать следующий пост.
docker compose -f bot/compose.yaml exec poster node bot/run.mjs --publish-next

# Остановка.
docker compose -f bot/compose.yaml stop
```

После изменения ключей, канала или расписания в `bot/.env` пересоздай контейнер:
`docker compose -f bot/compose.yaml up -d --force-recreate`.
Очередь перечитывается автоматически, её изменение не требует перезапуска.
Если канал не задан, контейнер работает в режиме ожидания без публикаций.

Контейнер запускается от пользователя `node`, без открытых портов, с файловой
системой образа только для чтения. Для Linux-хоста каталог `bot/data` должен быть
доступен на запись UID 1000. На macOS права проверены через Docker Desktop.

В журнале `sent` означает успешную публикацию, `empty` — очередь закончилась,
`rejected` — явный отказ Telegram, `uncertain` — неизвестен результат отправки.
Все уведомления об ошибках отправляются только в Telegram-чат `BOT_ALERT_CHAT_ID`.

## Ошибки, уведомления и восстановление

История в `bot/data/state.json` совместима с предыдущей версией и хранит также
причину ошибки, площадку, код API, число попыток и время следующего повтора. Не удаляй
историю: это защита от повторных публикаций. Для другого канала используй отдельный
`BOT_STATE_PATH`. Поддерживается локальная файловая система; сетевые файловые системы
и распределённая работа не поддерживаются.

- **429:** ждём не меньше `retry_after`, затем повторяем. Другие явные временные
  ошибки API (ответ `ok: false`, код 5xx) повторяем с растущей задержкой и небольшим
  случайным сдвигом. Максимум три попытки, включая первую. После исчерпания — `exhausted`.
- **401/403:** пост блокируется, Telegram приостанавливается. Исправь ключ или
  права, затем выполни `--resume-telegram`. Пауза относится только к Telegram;
  сохранённые посты с подтверждением Telegram могут продолжать отправку в ВК.
- **Некорректный пост / постоянный отказ:** `failed`. Остальная очередь продолжает
  работать в следующие слоты. Исправь пост и явно разреши повтор через `--retry-post`.
- **Обрыв связи, таймаут, невалидный ответ:** `uncertain`, автоматического повтора нет.
  Пост мог быть доставлен. Проверь канал перед ручным решением.
- **Авария после начала отправки:** при следующем запуске `sending` превращается в
  `uncertain`. Системный файловый замок освобождается ОС при завершении процесса;
  файл `state.json.lock` остаётся, это нормально. Его не нужно удалять. Блокировка
  работает и при длительной отправке, её нельзя украсть по таймауту.

Повторы сохраняются до сетевого запроса и переживают рестарт контейнера. Ожидающий
повтор Telegram задерживает следующие Telegram-посты, но не сохранённые доставки
в ВК. Повтор или пауза ВК не блокируют новые Telegram-выпуски. Ограничение частоты
применяется ко всей затронутой площадке. После паузы не догоняем старые слоты.
Восстановленные спорные посты не отправляются автоматически.

Команды из корня проекта:

```sh
# Состояния, причины ошибок и число попыток (без HTML постов и ключей).
docker compose -f bot/compose.yaml exec poster node bot/run.mjs --status

# Снять все паузы после исправления причин.
docker compose -f bot/compose.yaml exec poster node bot/run.mjs --resume

# Снять паузу только нужной площадки/источника очереди.
docker compose -f bot/compose.yaml exec poster node bot/run.mjs --resume-vk
docker compose -f bot/compose.yaml exec poster node bot/run.mjs --resume-telegram
docker compose -f bot/compose.yaml exec poster node bot/run.mjs --resume-queue

# Пост точно отсутствует: разрешить повтор. Само по себе сообщение не отправляет.
docker compose -f bot/compose.yaml exec poster node bot/run.mjs --retry-post POST_ID

# Пост уже есть в канале: отметить доставленным, указав номер сообщения.
docker compose -f bot/compose.yaml exec poster node bot/run.mjs --mark-sent POST_ID MESSAGE_ID
```

`--retry-post` сбрасывает лимит попыток при следующем выборе поста. Используй только
после проверки канала/исправления текста. `--publish-next` может сразу отправить
разрешённый пост; запланированный повтор не ускоряется этой командой.

Для уведомлений задай `BOT_ALERT_CHAT_ID` в `.env`. В личном чате сначала нажми Start
у бота. При паузе площадки или источника очереди, неизвестной доставке, блокировке поста и исчерпании
попыток отправляется одно уведомление на событие. Каждая неудачная попытка при временной
ошибке тоже создаёт уведомление, даже если последующий повтор успешен. Статус уведомления тоже сохраняется до сетевого запроса,
чтобы избежать спама после рестарта. Если Telegram/интернет недоступен или токен
отозван, уведомление тоже может не дойти: это отмечается в истории и журнале.
Явные временные отказы Telegram при отправке уведомления повторяются максимум три
раза с задержкой и учётом `retry_after`; это не блокирует доставку постов. При
неизвестном результате уведомление не повторяется автоматически, чтобы не спамить.
Журнал Docker остаётся резервным каналом
диагностики. Для уведомлений независимо от Telegram потребуется внешний мониторинг.

Повреждение файла состояния или отказ диска блокирует отправку; бот уведомляет
Telegram-чат и продолжает безопасно проверять состояние. Отдельный файл
`state.json.errors.json` подавляет повторные уведомления до восстановления. При
недоступности диска действует ограничение одним уведомлением на процесс. История
публикаций не сбрасывается автоматически.

## Последовательная публикация в ВК

После подтверждения Telegram бот сохраняет `messageId` и переключает запись на
`platform: vk`. Затем отправляет тот же материал обычным текстом со ссылкой через
`wall.post` (`owner_id=-VK_GROUP_ID`, `from_group=1`). Успех ВК сохраняется как
`vkPostId`; `sent` для новых постов с ВК означает завершение обеих площадок.
Ранее отправленные Telegram-посты автоматически в ВК не переносятся.

Если Telegram не подтвердил доставку, отправка в ВК не начинается. Сбой ВК не
повторяет Telegram: сохранённый текст и этап позволяют продолжить после рестарта
даже при удалении поста из очереди. Пока ВК ждёт повтора или исправления прав,
Telegram продолжает следующие выпуски, а ВК сохраняет очередь ожидающих постов.
После восстановления она обрабатывается по порядку; Telegram повторно не отправляется.
Три попытки допускаются отдельно для каждой площадки.

Подтверждённые временные ошибки отправки используют экспоненциальный бэкофф:
обычные сбои — от 60 секунд, Telegram 429 / VK 6 — от 120 секунд,
VK 9 (flood control) — от 15 минут, VK 29 (rate limit) — от часа.
Каждый следующий сбой удваивает задержку; добавляется случайный разброс до 25%.
Наш предел — 6 часов, но более длинный Telegram `retry_after` всегда соблюдается.
Это наша осторожная политика ожидания, а не объявленные VK сроки сброса лимитов.
Пауза и серия ошибок сохраняются на диск для каждой площадки проекта.
Новые посты и ручной запуск не обходят паузу, даже после исчерпания трёх попыток.
Серия сбрасывается после успешной отправки; явный `--resume` также снимает её.
Другая площадка и другие проекты продолжают работать независимо.
Ошибки авторизации, прав или CAPTCHA приостанавливают только ВК до `--resume-vk`.
Таймаут/неподтверждённый ответ остаётся `uncertain`: проверь сообщество вручную.
`guid` стабилен для выпуска, но защита от повторов не полагается на него.

`--status` показывает текущую площадку, Telegram `messageId` и ВК `vkPostId`.
Также он показывает отдельные `pauses` и `cooldowns` для площадок.
`--retry-post ID` при сбое ВК разрешает повтор **только ВК**.
`--mark-sent ID NUMBER` относится к текущей площадке: при этапе ВК указывай номер
VK-поста. При неизвестной доставке Telegram команда подтверждает Telegram и
оставляет ВК в ожидании отправки. Само подтверждение не выполняет сетевых запросов.
Для другой пары площадок используй отдельный файл состояния и сохраняй историю.

Некорректные настройки ВК изолируются паузой ВК; Telegram продолжает работать.
Несовпадение сообщества с сохранённым адресатом не перенаправляет старые посты:
ВК ставится на паузу, нужно восстановить правильный `VK_GROUP_ID`. Повреждение
исходной очереди запрещает новые выпуски до `--resume-queue`, но не мешает завершить
посты, уже сохранённые в истории. Повреждение самой истории или отказ записи на
диск блокирует обе площадки: отправлять без защиты от дублей нельзя.

Ключ сообщества проверен публикацией; удаление и редактирование этим ключом вернули
ошибку 27. Бот не пытается откатывать уже опубликованный Telegram-пост при сбое ВК.

## Генерация через OpenRouter

### Дайджест дважды в день

```dotenv
BOT_POST_SOURCE=openrouter
BOT_CONTENT_MODE=digest
BOT_TIMES=10:00,18:00
BOT_TIMEZONE=Europe/Moscow
```

Основной редакторский промпт: `bot/prompts/digest.md`. `BOT_PROMPT` задаёт тему
выпуска; общий промпт определяет отбор, точность, стиль и формат. Изменение файла
промпта требует пересборки образа; изменение `.env` — пересоздания контейнера.

Сначала бот собирает датированные публикации из лент первоисточников: инженерные
блоги, релизы coding tools и arXiv cs.SE. Читает текст/аннотацию, предоставленные
самим издателем. При нехватке кандидатов подключает встроенный native web search
через OpenRouter и читает доступные страницы найденных материалов; отдельного
аккаунта поискового сервиса нет. Список разрешённых доменов и лент хранится в
`bot/digest.mjs` и может расширяться.

Затем модель отбирает 5–10 материалов и делает русские описания-затравки; сами
источники могут быть русскими и английскими. Приоритет — последние 72 часа;
допускается расширение до 14 дней. Даты сохраняются для проверки, но не выводятся
в публикации. Пост начинается с одного заголовка с ключевыми темами выпуска, без
даты и вводного абзаца. В каждом пункте название, описание и ссылка разделены
пустыми строками. Telegram показывает ссылку «→ Читать источник», VK —
«→ Читать источник: URL». Код проверяет,
что дата присутствует в данных источника, URL выбран из найденных кандидатов,
нет дублей и будущих дат, не более трёх пунктов с одного домена и не более 3900
символов вместе с полными ссылками. Пометка «Препринт:» не выводится; описания исследований сохраняют условия и ограничения результатов. Ночные автоматические
релизы исключены; от одного GitHub-репозитория берётся последний стабильный релиз.

Ссылки последних 28 выпусков исключаются из кандидатов. Одно событие разными
ссылками всё ещё может повториться: редакторский промпт запрещает это, но код
гарантирует только отсутствие повторных адресов. Проверка источников и дат не
заменяет ручной фактчекинг всех утверждений модели. Если сильных материалов меньше
пяти, бот пропускает выпуск с уведомлением, а не заполняет его случайными ссылками.

Кандидаты кэшируются на час в `bot/data/digest-cache/`: повтор редакторской генерации
использует те же источники. Готовый текст сохраняется в истории до публикации;
повтор отправки не запускает новый поиск. Чтение лент бесплатно; веб-поиск и запросы
к модели оплачиваются из баланса OpenRouter. Цена дайджеста зависит от объёма
источников и использования поиска и существенно выше цены короткого совета.

`--generate-preview` проверяет выпуск без публикации. `--publish-next` создаёт
тестовый выпуск и публикует Telegram → ВК. Защитные паузы и уведомления работают
так же, как для коротких постов.

### Короткий совет

В локальном `.env`:

```dotenv
BOT_POST_SOURCE=openrouter
BOT_CONTENT_MODE=tip
OPENROUTER_API_KEY=ваш_ключ
OPENROUTER_MODEL=google/gemini-3.1-flash-lite
BOT_PROMPT=Напиши мне пост про вайбкодинг на 500 символов в нужном нам формате.
```

Модель по умолчанию — Gemini 3.1 Flash Lite: бюджетный вариант со структурированным
JSON-ответом. Локально запросы идут напрямую через VPN хоста; прокси не подключён.
Модель и пользовательский промпт можно менять в `.env`; после изменений пересоздай
контейнер. `BOT_POST_SOURCE=queue` возвращает ручную очередь без обращений к LLM.

Сейчас это самостоятельный совет про вайбкодинг: заголовок, основной текст,
«Зачем это», «Что попробовать». Ссылок на статьи и выдуманных источников нет.
Генератор получает JSON-схему; код проверяет поля и длину итогового текста:
цель — 500, допустимо 450–550 Unicode-символов, включая заголовки, пробелы и
переносы, без HTML-разметки. Текст не обрезается посреди предложения.
Недавние десять заголовков передаются модели для уменьшения повторов тем;
это не гарантирует смысловую уникальность.

```sh
# Настройки и промпт: без запроса к API и без расходов.
docker compose -f bot/compose.yaml exec poster node bot/run.mjs --dry-run

# Платная генерация для просмотра: без публикации и записи в историю доставки.
docker compose -f bot/compose.yaml exec poster node bot/run.mjs --generate-preview

# Сгенерировать и отправить следующий выпуск Telegram → ВК прямо сейчас.
docker compose -f bot/compose.yaml exec poster node bot/run.mjs --publish-next

# После исправления ключа, баланса или доступа к модели.
docker compose -f bot/compose.yaml exec poster node bot/run.mjs --resume-openrouter
```

В постоянном режиме генерация вызывается только для нового выпуска по расписанию.
До запроса сохраняются слот, ID и число попыток; результат сохраняется до отправки
в Telegram. Повтор доставки не вызывает новую генерацию. Даже авария между
сохранением текста и отправкой не теряет готовый выпуск.

Максимум три запроса генерации на выпуск, до 700 выходных токенов каждый. Таймаут,
временный отказ или некорректный JSON/длина дают повтор с задержкой; после третьего
сбоя выпуск пропускается с уведомлением. При корректировке длины модель получает
дополнительное указание. Ошибки ключа, оплаты и конфигурации ставят на паузу только
генератор до `--resume-openrouter`. Уже сохранённые доставки продолжают работать.
Все ошибки генерации отправляются в тот же Telegram-чат для ошибок. Цена и
число символов сохраняются в метаданных выпуска; ключ не сохраняется в истории.
Для маршрутизации задан верхний предел цены $0.30/M входных и $2/M выходных токенов;
при смене модели на более дорогую нужно осознанно изменить этот предел в коде.

Telegram API: https://core.telegram.org/bots/api#sendmessage

## Обложки по содержанию поста

```dotenv
BOT_IMAGES_ENABLED=true
OPENROUTER_IMAGE_MODEL=inclusionai/ming-image-0.1-design
VK_IMAGES_ENABLED=true
VK_PHOTOS_ACCESS_TOKEN=
```

Готовый текст отправляется прямо в image API OpenRouter с инструкцией «придумай
картинку для этого поста». Отдельного текстового LLM-запроса нет. Общий стиль и
правила иллюстрации заданы в `bot/prompts/cover.md`, сюжет выбирается по теме поста.
Ming Image на момент теста бесплатна; доступность и тариф могут измениться.
`bytedance-seed/seedream-4.5` можно выбрать через `OPENROUTER_IMAGE_MODEL`.

Изображение уменьшается до 1280×720 с сохранением пропорций; для результата с другим соотношением сторон добавляются поля. Обложка преобразуется в двухкадровый GIF и сохраняется в `bot/data/images/` до отправки. Кадры отличаются одним пикселем, чтобы GIF сохранялся как анимация. Существующий PNG-кэш преобразуется локально, без повторной генерации.
Повтор публикации использует сохранённый файл. Если процесс прервался во время
генерации, бот проверяет кэш и не запускает второй запрос: без готового файла
публикуется текст, владельцу приходит уведомление.

Telegram отправляет GIF и весь текст одним сообщением через `sendAnimation`.
Редактор выбирает пять сильных ссылок и пишет компактные описания: видимая подпись
целиком должна помещаться в 1024 символа. Код проверяет лимит до генерации обложки
и не публикует два отдельных сообщения. Скрытые URL не занимают место в подписи.
При превышении лимита редактор получает повторную попытку; вручную подготовленный
слишком длинный пост отклоняется с уведомлением владельца. Повтор после явного
временного отказа Telegram использует сохранённое фото. При неопределённой отправке
пост ожидает проверки оператором, чтобы не продублировать фото с подписью.
Ранее сохранённые выпуски с отдельной обложкой завершаются по старой схеме без
повторной отправки картинки.

VK публикует ту же GIF-обложку через `docs.getWallUploadServer` → загрузку с полем
`file` → `docs.save` → `wall.post`. Достаточно ключа сообщества `VK_ACCESS_TOKEN`
с правами `docs` и `wall`, включённого раздела «Файлы» и `VK_IMAGES_ENABLED=true`.
Пользовательский `VK_PHOTOS_ACCESS_TOKEN` для GIF не используется.
При ошибке загрузки VK публикует сохранённый текст; уведомление о сбое идёт в Telegram.
GIF отображается большим медиавложением с кнопкой воспроизведения.

### Старый режим пользовательских VK-токенов

Исторический режим: удалён из планировщика и production-образа. Текущий бот
не получает и не обновляет пользовательские токены VK. Ниже описан старый
локальный workflow; для GIF используются только ключи сообществ.

Если пользовательский токен истёк или VK вернул ошибку авторизации (код 5 / 27),
старые OAuth-утилиты могли отправлять в `BOT_ALERT_CHAT_ID` ссылку OAuth и просить
прислать полный URL после входа (`oauth.vk.ru/blank.html#access_token=...`).

Настройки:

```dotenv
VK_OAUTH_CLIENT_ID=54805806
BOT_OPERATOR_USER_ID=123456789
BOT_ALERT_CHAT_ID=...
```

`BOT_OPERATOR_USER_ID` — твой числовой Telegram user id (только этот аккаунт может
прислать ссылку). Токен сохраняется в `bot/data/vk-photos.token` (volume в Docker)
и при возможности обновляется `VK_PHOTOS_ACCESS_TOKEN` в `bot/.env`. Перезапуск
контейнера после обновления не обязателен.

Получить OAuth-ссылку нужно **с того же исходящего IP**, с которого бот ходит в VK
(для Docker — после входа сразу проверь из контейнера). Повторный запрос в Telegram
не чаще раза в час.

После изменения `.env` пересоздайте локальный контейнер:

```sh
docker compose -f bot/compose.yaml up -d --build --force-recreate
```

## Несколько проектов (этап 1, частично)

Декларативный конфиг в JSON: провайдеры, получатели, редакционные проекты.
Пример: `bot/service.example.json`. Секреты остаются в `.env`, в файле только
`*Env`-ссылки. Промпты — только внутри каталога конфига (обычно корень `bot/`).

```sh
# Проверить схему и ссылки
node bot/run.mjs --validate-config --config bot/service.example.json

# Список проектов и получателей
node bot/run.mjs --list --config bot/service.example.json

# Предпросмотр / публикация / статус для одного проекта
node --env-file=bot/.env bot/run.mjs --config bot/service.json --project coding-reading --dry-run
node --env-file=bot/.env bot/run.mjs --config bot/service.json --project coding-reading --generate-preview
node --env-file=bot/.env bot/run.mjs --config bot/service.json --project coding-reading --publish-next
```

В `.env` можно задать `BOT_CONFIG_PATH`. Старые переменные `TELEGRAM_*`, `VK_*`,
`BOT_TIMES` и т.д. продолжают работать без конфига. Если заданы и конфиг, и legacy-
переменные, CLI выведет предупреждение: приоритет у `BOT_CONFIG_PATH`.

Планировщик в multi-режиме обходит все включённые проекты; у каждого свой
`statePath` (см. поле в конфиге).
