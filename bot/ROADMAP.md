# План развития универсального автопостера

Дата: 5 октября 2026. Статус: план, перечисленные этапы ещё не реализованы.

Цель — один сервис для множества Telegram-каналов и VK-сообществ. У каждой
редакционной рубрики свои источники, промпты, расписание, провайдеры, бюджет и
получатели. Добавление канала должно требовать настройки, а не изменения кода.

## Что уже работает и где ограничения

- Локальный Docker-контейнер, расписание, ручная очередь и генерация через OpenRouter.
- Советы и дайджесты, проверка источников и дат, кэш кандидатов и история ссылок.
- Telegram → VK: текст и обложка 1280×720 одним сообщением в Telegram; VK в текущей
  конфигурации получает только текст. Ошибки направляются в Telegram-чат владельца.
- Сохранение результата до отправки, блокировка параллельных запусков, ограниченные
  повторы, отдельные паузы площадок и ручное разрешение неопределённой доставки.
- 69 тестов бота проходят на дату документа. Это проверка конкретных сценариев,
  а не измеренное подтверждение круглосуточной надёжности или масштабируемости.

Сейчас настройки глобальные: одна пара получателей, один редакционный процесс,
один файл состояния и общий цикл с блокировкой. Сетевая операция внутри этого
цикла может задержать следующую работу. OpenRouter, поиск, промпты и лимиты тесно
связаны с текущими форматами. Изоляция пауз не означает полной изоляции времени
выполнения, хранилища и учётных данных. Много каналов одним экземпляром пока не поддерживается.

## Основные решения

1. Отделить редакционный проект от площадки доставки. Проект готовит выпуск;
   один выпуск можно доставить в несколько каналов с отдельным оформлением.
2. Разделить поиск, редактирование, картинки, форматирование и доставку на этапы.
   У каждого этапа свои таймауты, бюджет, состояние и правила повторов.
3. Хранить нормализованный материал отдельно от Telegram HTML и VK-текста.
   Изменение оформления получателя не должно заново запускать LLM.
4. Сделать конфигурацию декларативной и версионируемой, секреты передавать отдельно.
5. Сначала использовать один сервис и SQLite с устойчивой очередью задач.
   Выделять отдельные сервисы, PostgreSQL или брокер после измерения ограничений.
6. Считать безопасную остановку лучше неподтверждённой повторной публикации.
   Сквозную гарантию exactly-once не обещать: внешнее API может принять пост и
   потерять ответ. Такие доставки требуют сверки или решения оператора.

## Модель конфигурации

| Сущность            | Ответственность                                                               |
| ------------------- | ----------------------------------------------------------------------------- |
| Редакционный проект | Тема, язык, рубрика, промпты, поиск, качество, расписание и бюджет            |
| Профиль провайдера  | Адаптер API, модель, ссылка на секрет, лимиты, возможности и резерв           |
| Получатель          | Площадка, адресат, учётные данные, оформление, медиа и политика доставки      |
| Выпуск              | Слот, снимок настроек, проверенные источники, результат и стоимость генерации |
| Доставка            | Один выпуск одному получателю, попытки, подтверждение, ошибка и история       |

Один проект может питать несколько получателей; один канал может получать разные
рубрики с контролем общего расписания и частоты. Если двум каналам нужны разные
темы или тексты, это разные редакционные проекты, а не один переиспользуемый выпуск.

Ниже пример **будущего** формата; текущий бот этот файл ещё не читает. Имена
адаптеров и параметры предстоит реализовать и валидировать.

```yaml
version: 1
providers:
  budget-editor:
    adapter: openrouter
    model: google/gemini-3.1-flash-lite
    credentialEnv: OPENROUTER_API_KEY
  alternative-editor:
    adapter: openai-compatible
    baseUrlEnv: SECOND_LLM_BASE_URL
    modelEnv: SECOND_LLM_MODEL
    credentialEnv: SECOND_LLM_API_KEY
destinations:
  coding-telegram:
    platform: telegram
    chatIdEnv: CODING_TELEGRAM_CHAT_ID
    credentialEnv: TELEGRAM_BOT_TOKEN
    media: { enabled: true, width: 1280, height: 720 }
  coding-vk:
    platform: vk
    groupIdEnv: CODING_VK_GROUP_ID
    credentialEnv: VK_ACCESS_TOKEN
    media: { enabled: false }
projects:
  coding-reading:
    enabled: true
    format: digest
    language: ru
    sourcesProfile: coding-primary-sources
    prompts:
      editor: prompts/coding/editor.md
      cover: prompts/coding/cover.md
    generation:
      provider: budget-editor
      fallbackProviders: [alternative-editor]
    schedule:
      timezone: Europe/Moscow
      times: ['10:00', '18:00']
      missedSlots: skip
    delivery:
      policy: ordered-independent
      destinations: [coding-telegram, coding-vk]
    budget: { dailyUsd: 2, monthlyUsd: 30 }
```

Промпты описывают редакционные требования; безопасность, адресаты, лимиты и
права доступа задаются кодом и конфигурацией. Ответ модели не может менять их.
В выпуске фиксируются версия конфигурации, хеш промпта, модель и источники.
Изменения применяются к новым выпускам; существующий выпуск завершается по
сохранённым настройкам. Замена адресата не перенаправляет старую очередь.

## Этап 1. Конфигурация нескольких проектов и получателей — P0

- [ ] Ввести JSON Schema и загрузчик конфигурации: уникальные ID, ссылки между
      сущностями, часовые пояса, расписания, пути промптов, форматы и диапазоны бюджетов.
- [ ] Разрешать пути промптов только внутри каталога конфигурации; запретить
      произвольные команды, секреты в файлах и непроверенные адреса API.
- [ ] Выделить глобальные настройки сервиса и собственные настройки каждого проекта.
      Не наследовать скрыто чужую модель, получателей или промпт.
- [ ] Добавить `validate`, `list`, `preview --project`, `publish --project`
      и статус с фильтрами проекта, получателя и выпуска.
- [ ] Ошибка проекта приостанавливает этот проект; общая ошибка хранилища
      безопасно останавливает публикации всего сервиса.
- [ ] Определить правила пересечений расписаний и минимальный интервал публикаций
      в одном канале, включая ручные выпуски.
- [ ] Оставить текущий `.env` совместимым на время миграции и выдавать явное
      предупреждение, если заданы одновременно старые и новые настройки.

**Готово, когда:** три проекта с разными темами и расписаниями работают с шестью
получателями без правок кода; некорректный проект не влияет на два остальных;
предпросмотр не отправляет посты и явно сообщает о платных запросах генерации.

## Этап 2. Устойчивая очередь и независимая доставка — P0

- [ ] Перенести JSON-историю в SQLite: проекты, выпуски, задачи, источники,
      генерации, доставки, события и миграции схемы.
- [ ] Создавать слот и задания транзакционно. Уникальные ограничения:
      `(project_id, slot_utc)` для выпуска и `(edition_id, destination_id)` для доставки.
- [ ] Использовать ограниченные по времени аренды задач и атомарное получение
      работы. Завершить сетевую операцию до освобождения задачи; старый работник
      не должен записывать результат после потери аренды.
- [ ] Сделать отдельную машину состояний доставки: `pending`, `sending`,
      `retry_wait`, `sent`, `uncertain`, `failed`, `cancelled`. Подтверждение
      хранит ID сообщения, время и адресата.
- [ ] Разделить политики: независимая рассылка; последовательная отправка, где
      терминальный отказ первого адресата не отменяет остальных; строгая цепочка,
      где следующая площадка требует подтверждения предыдущей. Не менять текущую
      последовательность Telegram → VK молча при миграции.
- [ ] Неопределённый результат блокирует повтор этой доставки. Для строгой цепочки
      он также блокирует зависимые доставки; независимые проекты продолжают работу.
- [ ] Ошибки и ограничения изолировать по получателю, проекту, провайдеру и
      общему ключу API. Один Telegram-токен используется несколькими каналами:
      его лимит нужно учитывать совместно.
- [ ] Сохранить платную генерацию, проверку качества и медиа до начала доставки.
      Повтор публикации не меняет выпуск и не вызывает LLM.
- [ ] Добавить безопасные команды сверки, подтверждения, повторной отправки и
      отмены с журналом действий; не сбрасывать состояние массово.
- [ ] Перед миграцией сделать резервную копию JSON, проверить число записей,
      подтверждения и адресатов. Никаких ретроспективных публикаций уже отправленных постов.

**Готово, когда:** аварийное завершение в каждой границе «сохранение → API →
подтверждение» не вызывает автоматического дубля; два работника не отправляют
одну задачу; сбой одного канала не останавливает другие; миграция сохраняет
все квитанции текущего Telegram и VK. Отдельно проверяется восстановление
`uncertain` без повторной генерации и без изменения адресата.

## Этап 3. Провайдеры LLM и управление расходами — P1

- [ ] Ввести интерфейсы текстовой генерации, поиска и изображений отдельно:
      входные данные, результат, usage, стоимость, request ID и нормализованная ошибка.
- [ ] Начать с адаптера OpenRouter и одного альтернативного провайдера.
      OpenAI-совместимость считать базовым транспортом: поддержка JSON Schema,
      изображений, поиска и лимитов проверяется отдельно для конкретной модели.
- [ ] Добавить реестр возможностей: структурированный вывод, контекст, поиск,
      картинки, размеры и поддерживаемые параметры. Несовместимые сочетания
      отклонять до платного запроса.
- [ ] Разрешить собственные модели и промпты для поиска, редактора и обложки
      каждого проекта. Хранить версии и историю изменения промптов.
- [ ] Сделать резервные провайдеры явными: перечень допустимых ошибок, число
      попыток, общий срок задачи, предельная стоимость и допустимая передача данных.
      Не заменять модель молча при отказе оплаты или несовместимости параметров.
- [ ] Перед запросом резервировать бюджет; после ответа учитывать фактическую
      стоимость. Для неизвестной стоимости или оборванного платного запроса оставлять
      консервативный резерв до сверки. Не считать отсутствие usage бесплатным запросом.
- [ ] Ввести лимиты на выпуск, сутки и месяц по проекту и по ключу провайдера;
      учитывать поиск, исправление невалидного ответа, запасную модель и картинку.
- [ ] Настраивать VPN/прокси и таймауты на уровне профиля провайдера. Локально
      оставить прямое подключение; продакшен-прокси не делать общей зависимостью доставки.

**Готово, когда:** два проекта используют разные провайдеры; исчерпание бюджета
одного не блокирует другой; резервный провайдер не превышает общий лимит;
доставка сохранённого выпуска работает без доступного LLM.

## Этап 4. Качество материалов и оформление — P1

- [ ] Вынести тематические профили источников из кода. Настроить языки, свежесть,
      минимальное число материалов, приоритет первоисточников и ограничения доменов.
- [ ] Кэшировать источники по URL и параметрам запроса с TTL, ETag/Last-Modified,
      ограничениями объёма и времени чтения; безопасно проверять каждый редирект.
- [ ] Помимо URL отслеживать одно событие, DOI/arXiv ID и релиз репозитория;
      разделить историю повторов проекта и конкретного канала.
- [ ] Создать набор эталонных материалов и проверять промпты: реальность ссылок,
      даты, соответствие описания источнику, практическая полезность и отсутствие повторов.
      Автоматические проверки дополнять выборочной ручной оценкой.
- [ ] Поддержать типы публикаций: дайджест, короткий совет, разбор инструмента и
      ручной материал через общий нормализованный документ.
- [ ] Настроить оформление отдельно по адресату: ссылки, заголовки, подпись,
      лимиты площадки, картинки и политика слишком длинного текста.
- [ ] Сохранить текущий режим: Telegram — одна обложка 1280×720 с подписью,
      VK — текст. Для длинных подборок выбирать явную политику: компактная версия,
      несколько сообщений или отсутствие картинки; не разрезать пост незаметно.
- [ ] Ввести предпросмотр итоговой версии для каждой площадки и необязательную
      очередь ручного утверждения. Проверки содержания не должны читать секреты.

**Готово, когда:** один выпуск получает разные проверенные представления для
Telegram и VK; невалидный URL и превышение лимита запрещают соответствующую
доставку до исправления; отсутствие сильных источников не заполняется выдумками.

## Этап 5. Надёжность, безопасность и эксплуатация — P0/P1

- [ ] Ограничить время каждого этапа и всей задачи; использовать отмену запросов,
      повторы с экспоненциальной задержкой и случайным разбросом. Уважать `retry_after`.
      Не повторять ошибки прав, оплаты, CAPTCHA и неопределённой доставки автоматически.
- [ ] Ограничить общую параллельность, отдельные пулы поиска/LLM/картинок/доставки
      и очереди по проектам. Длинная генерация не должна удерживать блокировку доставки.
- [ ] Реализовать временное отключение неисправного провайдера с пробными запросами
      восстановления; не смешивать его с паузой конкретного получателя.
- [ ] Добавить структурированные события: project/edition/task/destination ID,
      этап, попытка, задержка, код ошибки, стоимость. Секреты, заголовки авторизации
      и полные ответы с чувствительными данными не записывать.
- [ ] Метрики: возраст очереди, опоздание слота, доля доставок, `uncertain`,
      время стадий, стоимость, кэш, размер хранилища и частота подавленных уведомлений.
- [ ] Все уведомления об ошибках отправлять только в Telegram-бот для ошибок,
      с настройкой маршрута по проекту. Группировать повторные инциденты; закрытие
      инцидента сообщать один раз. При недоступном Telegram сохранять событие и
      локально писать сигнал для оператора, не блокируя публикации.
- [ ] Разделить проверку процесса, готовности хранилища и состояния очереди.
      Ошибка одного внешнего API не должна вызывать бесконечные перезапуски контейнера.
- [ ] Проверять секреты и права при подключении адресата без публикации тестового
      поста; поддержать ротацию ключей и минимально необходимые права.
- [ ] Источники считать недоверенными данными: защита от prompt injection,
      SSRF, приватных IP, DNS-подмены, редиректов, больших документов и опасных изображений.
      Ответ модели не может выполнять команды или определять URL API.
- [ ] Ввести ограничение роста кэша, изображений и журналов; хранить квитанции
      и ключи дедупликации дольше самих медиа. Очистка не затрагивает активные задачи.
- [ ] Настроить резервные копии SQLite согласованным способом, проверку целостности
      и регулярное восстановление в отдельный каталог. Не копировать живой DB-файл
      отдельно от WAL. Восстановление старой копии требует сверки публикаций после неё.
- [ ] Добавить инструкцию аварийной остановки, проверки неопределённых отправок,
      восстановления, отката версии и изменения расписания. Завершение SIGTERM
      прекращает получение задач и безопасно сохраняет незавершённые операции.

**Готово, когда:** испытания обрыва сети, 429/5xx, истёкшего токена, неверного JSON,
заполненного диска, повреждённого состояния и SIGKILL имеют ожидаемый результат;
секреты не появляются в логах и артефактах; восстановление из копии выполнено
на практике и не запускает публикации до проверки возможных дублей.

## Этап 6. Оптимизация и проверка масштаба — P2

- [ ] Снять исходный профиль CPU, памяти, времени этапов, объёма хранилища и
      расходов; оптимизировать только измеренные узкие места.
- [ ] Переиспользовать поиск между проектами с одинаковыми профилями источников,
      сохраняя раздельный редакционный отбор, бюджет и историю повторов.
- [ ] Передавать редактору ограниченные выдержки; сокращать число платных
      исправлений валидацией входа и проверенными схемами ответа.
- [ ] Добавить индексы очереди и постраничное чтение истории вместо полного
      загрузочного чтения всех записей; ограничить размеры ответов и файлов.
- [ ] Проверить честное распределение работы: большой проект не вытесняет малый.
      При перегрузке откладывать работу в пределах политики слота, не увеличивать
      бесконтрольно число сетевых запросов.
- [ ] Измерить предел одного узла. Переход к нескольким узлам требует общего
      хранилища, координации аренд и лимитов; SQLite-файл на сетевом диске не является
      планом горизонтального масштабирования.

### Предлагаемые измеримые критерии

Это начальные цели для будущего стенда, а не текущие показатели. До испытания
фиксируем версию, оборудование, число работников, входные данные и ограничения
API. Отчёт включает сырые измерения, p50/p95/p99 и стоимость; цели пересматриваются
явно по результатам, а не объявляются достигнутыми по наличию тестов.

| Проверка        | Начальная цель                                                                                                                      |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Планировщик     | 100 проектов, 200 получателей, 50 одновременно готовых задач; p95 получения готовой задачи ≤ 5 с на стенде с имитацией API          |
| Изоляция        | 10 % адресатов отвечают 429/5xx; здоровые адресаты продолжают обработку, их p95 растёт не более чем на 20 % при той же нагрузке     |

Имитация API проверяет поведение очереди, но не фактические лимиты Telegram,
VK или LLM. Платные и публикующие проверки выполняются отдельно на тестовых
получателях с заранее ограниченным бюджетом и отдельными ключами.

## Порядок внедрения и общий Definition of Done

1. Конфигурация и схема данных: этап 1, миграция и инварианты этапа 2.
2. Изоляция работников, очередь, повторы и диагностика: этапы 2 и 5.
3. Второй провайдер, бюджеты и редакционные профили: этапы 3 и 4.
4. Восстановление, пилот, измерения и оптимизация: этапы 5 и 6.

Каждый этап выпускается с совместимой миграцией, обновлённой инструкцией,
предпросмотром и проверкой сохранённой истории. Перед переходом текущего бота:

- [ ] Резервная копия и проверка восстановления завершены.
- [ ] Набор тестов доставки и аварийных сценариев проходит без обращения к живым API.
- [ ] Миграция на копии состояния сохраняет адресатов и квитанции.
- [ ] Тестовый проект проверен, после него подключены два разных редакционных проекта.
- [ ] Бюджеты, ограничения, паузы и команды оператора проверены на этих проектах.
- [ ] Ключи, `.env`, история доставки и реальные материалы исключены из Git и образа.
- [ ] Отчёт пилота отделяет измеренные показатели от оставшихся целей и ограничений.

Админ-панель, дополнительные соцсети, автоматическое изменение промптов и
автоматическая оценка качества второй моделью — последующие расширения.
Они не должны задерживать устойчивую очередь, изоляцию проектов и контроль расходов.
