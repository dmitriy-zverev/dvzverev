# Будущий AI-бот для Telegram-канала

Статус: идея зафиксирована, не входит в первую версию лендинга  
Назначение: готовить и публиковать контент в Telegram-канал Дмитрия с помощью AI-провайдера, например OpenRouter.

## 1. Граница системы

Лендинг и бот — два независимых продукта:

```text
www.dvzverev.ru                 content bot
┌─────────────────────┐         ┌───────────────────────────┐
│ static HTML/CSS/JS  │         │ Python worker            │
│ без секретов и API  │         │ AI provider + Telegram   │
└─────────────────────┘         └───────────────────────────┘
          │                                  │
          └── обычная ссылка на канал ───────┘
```

Бот не добавляет JavaScript, API-запросы или runtime-зависимости на сайт. Он разворачивается позже как отдельный сервис, даже если физически работает на том же VPS.

## 2. Первая полезная версия

Основной сценарий:

1. Дмитрий отправляет боту тему, заметку, ссылку или тезисы.
2. Бот формирует черновик с учётом выбранного формата и tone of voice.
3. Бот показывает предпросмотр в личном чате.
4. Дмитрий выбирает: `Опубликовать`, `Переписать`, `Изменить`, `Запланировать` или `Отменить`.
5. После подтверждения бот публикует запись в Telegram-канале.
6. Сервис сохраняет идентификатор публикации и состояние задачи.

По умолчанию AI никогда не публикует первый вариант без подтверждения человека. Полностью автоматический режим можно добавить отдельно для безопасных повторяемых рубрик.

## 3. Возможности по этапам

### MVP

- входящие тезисы от владельца;
- генерация одного черновика;
- короткий и длинный формат;
- ручное редактирование;
- preview перед публикацией;
- публикация сразу или по времени;
- защита от повторной отправки;
- журнал состояний и ошибок.

### Следующий этап

- библиотека рубрик: backend, безопасность, разработка продуктов, разборы проектов;
- несколько вариантов заголовка;
- адаптация длинного текста в короткий пост;
- контент-план на неделю;
- серия связанных публикаций;
- прикрепление изображений;
- повторное использование подтверждённых фактов из портфолио;
- статистика публикаций через доступные Telegram-механизмы.

### Только после проверки качества

- полностью автоматические публикации по расписанию;
- обработка внешних источников и RSS;
- автоматическая генерация изображений;
- кросспостинг на другие платформы;
- автономный выбор темы.

## 4. Предлагаемая архитектура

Для первой версии достаточно одного модульного Python-сервиса, а не набора микросервисов.

```text
Telegram admin chat / scheduler
               │
               ▼
      application use cases
  create draft / revise / approve / publish
        │              │              │
        ▼              ▼              ▼
  ContentStore     AIProvider     ChannelPublisher
        │              │              │
   SQLite/Postgres  OpenRouter      Telegram Bot API
```

### Внутреннее ядро

- `Draft` — тема, исходные материалы, версия текста, статус;
- `Publication` — канал, время, Telegram message ID, результат;
- `ContentPolicy` — tone of voice, запрещённые утверждения, требования к ссылкам;
- use cases: создать черновик, переписать, одобрить, запланировать, опубликовать, повторить после временной ошибки.

### Порты

- `AIProvider` — генерация и редактирование текста;
- `ChannelPublisher` — preview и публикация;
- `ContentRepository` — черновики, версии и статусы;
- `Scheduler` — отложенные задачи;
- `Clock` — время для тестов;
- `SourceReader` — чтение внешнего источника, если появится позже.

### Адаптеры первой версии

- OpenRouter как один из адаптеров `AIProvider`;
- Telegram Bot API как `ChannelPublisher`;
- SQLite для простого старта или PostgreSQL после проверки инфраструктуры VPS;
- встроенный scheduler или отдельная очередь только при реальной необходимости.

Выбор OpenRouter не должен проникать в application/domain слой. Смена провайдера не меняет сценарии подготовки и публикации.

## 5. Технологический вариант

С учётом текущего стека Дмитрия:

- Python;
- Pydantic для конфигурации и DTO;
- Telegram bot library выбирается перед реализацией;
- `httpx` с одним переиспользуемым клиентом для внешних API;
- FastAPI нужен только при выборе webhook или отдельного admin API;
- SQLite для MVP либо PostgreSQL при наличии обоснованной многопользовательской/операционной нагрузки;
- Alembic при использовании SQL-базы с развивающейся схемой;
- Docker Compose для изоляции от статического сайта;
- структурированные логи и healthcheck.

Новые библиотеки и версии выбираются только перед реализацией по актуальной официальной документации.

## 6. Безопасность и секреты

- ключ OpenRouter хранится только в secret/environment на VPS;
- Telegram bot token хранится отдельно от конфигурации сайта;
- ни один секрет не попадает в frontend, Git, Docker image или логи;
- bot принимает управляющие команды только от allowlist Telegram user IDs;
- bot публикует только в заранее разрешённый channel ID;
- перед публикацией повторно проверяется автор и статус `approved`;
- внешние страницы и пользовательский текст считаются недоверенными данными, а не инструкциями для модели;
- лимиты стоимости и количества генераций настраиваются обязательно;
- чувствительные данные удаляются из логов;
- webhook, если будет, получает проверяемый secret path/header и HTTPS.

## 7. Надёжность публикации

- у каждой публикации есть idempotency key;
- повтор worker не создаёт второй пост после успешной отправки;
- временные ошибки получают ограниченные retries с backoff;
- постоянные ошибки переводят задачу в `failed` и уведомляют владельца;
- AI-генерация и Telegram-публикация — разные шаги и разные статусы;
- хранится последняя одобренная версия текста;
- удаление или изменение уже опубликованного поста требует отдельного подтверждения;
- расписание хранится в UTC, интерфейс показывает Europe/Moscow.

## 8. Контроль качества контента

Перед подтверждением бот показывает:

- итоговый текст;
- использованные исходные материалы;
- ссылки;
- потенциально непроверенные утверждения;
- предполагаемую рубрику и время публикации.

Для технического контента действует правило: модель помогает с формой, но факты о проектах, опыте и результатах берутся только из подтверждённой базы. Документ [content-inventory.md](./content-inventory.md) может стать начальной редакционной базой, но не должен автоматически отправляться внешнему провайдеру целиком.

## 9. Размещение на VPS

Будущий вариант:

```text
/srv/dvzverev/site/releases/...     static landing
/srv/dvzverev/content-bot/...       separate container/service
```

- разные release-процессы;
- разные переменные окружения;
- бот не имеет права записи в файлы production-сайта;
- web server продолжает отдавать лендинг как чистую статику;
- worker запускается отдельным systemd unit или Docker Compose service;
- сбой и перезапуск бота не влияют на доступность `www.dvzverev.ru`.

## 10. Решения, которые понадобятся позже

1. Ссылка и тематика Telegram-канала.
2. Ручное подтверждение навсегда или возможность автопубликации для отдельных рубрик.
3. Форматы входа: текст, голос, ссылки, файлы.
4. Нужна ли генерация изображений.
5. Частота публикаций и месячный AI-бюджет.
6. Предпочитаемые модели и fallback-провайдер.
7. SQLite или PostgreSQL после инвентаризации VPS.
8. Long polling или webhook.
9. Нужна ли связь с контентом лендинга.

До принятия этих решений бот остаётся независимым roadmap-пунктом и не блокирует запуск сайта.
