# Фича 3. Недельный импорт VK, месячная аналитика и улучшение промптов

Статус: план. Приоритет: P1, большая фича после общего реестра и приватного API.
Зависимости: [дашборд](01-weekly-dashboard.md), [общие данные](README.md).

## Результат для владельца

Раз в неделю владелец загружает статистику VK в кабинет, проверяет сопоставление
и подтверждает импорт. Видно, какие конкретные посты за последние 30 дней дают
охват и реакции, как связаны результаты с темой, временем, GIF, моделью и версией
промпта. Бот получает структурированные данные для предложений по редакции.

Новые промпты применяются по решению владельца, с версией и возможностью отката.
Аналитика не переписывает рабочие промпты и не меняет расписание сама.
Обучение весов модели, fine-tuning API и сбор пользовательских VK-токенов не входят в эту фичу.

## Исходные ограничения

Текущий `metrics.mjs` умеет hourly-снимки подписчиков, per-group/per-post JSON-импорт,
сверку валют и учёт генерации. Это переиспользуется, а не создаётся повторно.
`METRICS.md` фиксирует отсутствие доступа к wall/stats через наши community keys;
не строить новый модуль в расчёте на автоматически доступный охват.

Формат настоящего VK-экспорта пока не предоставлен. Первый этап — получить
обезличенный файл, определить единицы, заголовки, накопительные/периодные метрики
и сделать fixture. CSV UTF-8 и текущий JSON — MVP; XLSX добавляется отдельным
адаптером после проверки реального файла и влияния библиотеки на образ/API.
Если выгрузка не содержит post_id/ссылку, автоматическое точное сопоставление не обещается.

## Сценарий загрузки

1. Выбрать сообщество, неделю отчёта и время фактического наблюдения (`observed_at`).
2. Загрузить файл либо скачать шаблон и заполнить вручную. Показать ожидаемые поля,
   timezone и значение пустой ячейки: «нет данных», а не ноль.
3. Прочитать файл в изолированном обработчике, проверить объём/кодировку/schema.
4. Показать preview: строки, найденные посты, дубли, ошибки, неизвестные ID,
   изменившиеся значения, покрытие периода и группы. Ничего ещё не применять.
5. Для каждой строки найти `(vk_group_id, vk_post_id)` или извлечь из wall-ссылки.
   Заголовок/текст/дата — только подсказки для ручного выбора, не доказательство совпадения.
6. Подтвердить импорт. Все принятые строки и аудит записать одной транзакцией.
   При изменении файла или состояния после preview — повторить preview.
7. Показать результат: применено N, пропущено N, ошибок N, сколько постов без статистики.
8. Пересчитать панели и предложить анализ после успешного commit. Ошибка LLM-анализа
   не отменяет импорт и не влияет на доставку постов.

Невалидные строки по умолчанию блокируют commit. Режим «импортировать только
валидные» требует явного выбора и сохраняет список исключений. Не делать молчаливый partial import.
Данные чужой группы отклоняются. Посты, созданные вручную в VK, могут стать внешними
записями с ID/датой, без выдуманного текста и версии промпта; учитываются отдельно от постов бота.

## Контракт статистики

| Поля                                           | Значение и источник                                                 |
| ---------------------------------------------- | ------------------------------------------------------------------- |
| group_id, post_id, published_at                | Идентичность поста, время из реестра/экспорта                       |
| observed_at, period_from/to, metric_mode       | Когда измерено; cumulative или period                               |
| views                                          | Просмотры/показы согласно определению конкретной выгрузки           |
| reach_total, reach_organic, reach_paid         | Охват; рекламный и органический отдельно, если доступны             |
| likes, comments, reposts, saves                | Счётчики каждого вида, неизвестные — null                           |
| clicks, link_clicks                            | Тип переходов с обязательным определением, не смешивать разные поля |
| subscribers_at_publish                         | Ближайший известный снимок не позже публикации; отсутствие — null   |
| ad_spend, promoted                             | Расходы и признак продвижения, если предоставлены                   |
| import_id, source, source_hash, schema_version | Происхождение, аудит и воспроизводимость                            |

Коммерческие orders/revenue/commission остаются отдельным импортом, как сейчас.
Заказ не вычисляется из лайка или клика. USD расходов провайдера и RUB продаж
не складываются без явного курса/сверки. Не импортировать персональные данные покупателей.

Идентичность наблюдения: `(project_id, post_id, source, observed_at, metric_mode, period)`.
Одинаковый файл определяется hash + проектом + scope; повтор не удваивает значения.
Накопительная статистика одного поста за разные недели — последовательные snapshots,
а не суммы. Исправление того же наблюдения создаёт revision с заменой значений.
Периодные показатели складываются только на непересекающихся интервалах и при
совпадающих определениях; пересечения требуют исправления, а не автоматической арифметики.
Групповой итог не прибавляется к per-post строкам второй раз.

Снижение cumulative-счётчика показать как correction/аномалию, не запретить
безусловно: выгрузка может содержать пересмотр данных. Требуется подтверждение.
Файл с датой наблюдения раньше публикации, отрицательными счётчиками или
невалидными датами блокируется. Дробные просмотры/лайки не принимаются.

## Хранилище всех выпусков

Предлагаемые таблицы:

| Таблица                          | Назначение                                                  |
| -------------------------------- | ----------------------------------------------------------- |
| editions / post_content          | Выпуск, бриф, финальный текст, характеристики и TTL         |
| deliveries / delivery_tombstones | Получатель, внешний ID, подтверждения и защита от дублей    |
| generation_runs                  | Модель, роль, стоимость, latency, исход и связи с выпуском  |
| prompt_versions                  | Версия editor/reviewer/scene/video, hash и дата активации   |
| post_features                    | Тип, тема, язык, длина, медиа planned/actual, время, модель |
| metric_observations              | Per-post снимки и определения единиц                        |
| imports / import_rows            | Preview, revisions, provenance, сопоставление и commit      |
| experiments / recommendations    | Гипотезы, назначения вариантов, решения и результаты        |
| monthly_aggregates               | Итоги без текстов и per-post подробностей за пределами TTL  |

Материал сохраняется до внешней отправки. В версии фиксируется **точный текст,
который отправили**, а не позднее отредактированный промпт или новая генерация.
Доставка хранит фактическое text/GIF, включая fallback; плановое GIF не считается
реальной GIF в сегменте. До начала генерации фиксируются версии всех промптов,
моделей, config и выбранный experiment variant. Для старой истории версии
обозначаются `unknown`, текущий промпт не приписывается задним числом.

Содержимое из существующих JSON, queue/cache, previews, error-сообщений и backup
входит в аудит retention: одного удаления строки SQLite недостаточно.

## Хранение только последних 30 дней

Окно — rolling 30 × 24 часа по UTC; отображение дат по Москве. Дефолт отчёта —
«последние 30 дней», а не обещание полного календарного месяца из 31 дня.
Календарный месяц показывает фактическое покрытие и доступные агрегаты отдельно.

| Данные                                                  | Политика                                                                                  |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Опубликованный текст, бриф и медиа                      | Удалить по published_at + 30 дней                                                         |
| Черновик, неуспешная/неопределённая генерация           | Срок от created_at + 30 дней; нельзя держать текст вечно из-за ошибки                     |
| Per-post наблюдения и подробные рекомендации с цитатами | Удалить вместе с содержимым; до удаления свернуть в агрегаты                              |
| Сырые импортированные файлы/preview                     | Удалить после commit в течение 24 ч; отклонённые — также ≤ 24 ч                           |
| Минимальный audit импорта                               | Hash, даты, число строк, revision; без исходных текстов/персональных данных               |
| Технические tombstones                                  | До 90 дней без текста/медиа: slot, ID, получатель, исход, время, hash                     |
| Незавершённый uncertain                                 | Компактный incident без содержимого до ручного разрешения; автоматический повтор запрещён |
| Обобщённые месячные итоги и общие версии промптов       | Можно сохранять дольше, без старых текстов и примеров из удалённых постов                 |

TTL удаляет локальные копии, **не удаляет опубликованный пост со стены VK**.
Для expired pending-публикации прекратить автоматическую отправку и зафиксировать
`expired/cancelled`; нельзя после удаления текста внезапно заново генерировать
материал под прежним delivery_id. Операционный incident остаётся без payload.

Планировщик очистки: hourly, API сразу скрывает expired-контент даже до физической
очистки. Физическое удаление завершить не позже cutoff + 1 час при работающем хосте.
Очистка проверяет reference/lease, отменяет старые задания и не удаляет используемый
файл посреди отправки. При рестарте выполнить overdue cleanup до новых отправок.

Удаление должно охватывать текст в JSON-legacy, GIF/video, временные файлы,
SQLite WAL/journal/free pages, backend-кэши, сохранённые отчёты с цитатами и backups.
Подобрать и проверить secure-delete/checkpoint/compaction-процедуру для выбранного
адаптера; простое SQL DELETE не объявлять физическим стиранием файла базы.
Восстановление backup запускает TTL до API/планировщика. Старые migration-архивы
с содержимым из текущего развёртывания тоже требуют очистки/истечения.

Согласованная backup-политика: хранение до 7 дней, регулярная очистка; payload
шифруется ключом с expiry не позже content_expires_at. Если это не реализовано,
backup с текстами, пересекающий cutoff, должен быть удалён. Обещать 30-дневное
окно только после проверки всех копий, а не только главной таблицы.

## Аналитический кабинет

Вкладки: «Обзор 30 дней», «Все посты», «Импорты и покрытие», «Сегменты»,
«Промпты и эксперименты». Фильтры: проект, период, тип, тема, слот, медиа,
модель, prompt version, источник, organic/paid и возраст наблюдения.

Показывать:

- Каждый пост: точный текст, ссылка VK, дата, фактическое медиа, признаки,
  доступные метрики, стоимость и история ошибок.
- Топ/низ результатов с количеством наблюдений и явной полнотой данных;
  пост без метрик не занимает последнее место как нулевой.
- Динамику по дням/неделям и распределения, медианы и разброс, не только среднее.
- Покрытие: N постов с охватом из M отправленных, возраст статистики и пропуски.
- Органический результат отдельно от платного; нельзя объявить рост после
  рекламы победой нового промпта.

| Производная метрика       | Формула / условие                                                                   |
| ------------------------- | ----------------------------------------------------------------------------------- |
| Engagement/reach          | (likes + comments + reposts + saves) / reach; нужны все слагаемые и ненулевой reach |
| Link CTR                  | link_clicks / views или другой согласованный знаменатель; определение явно в UI     |
| Охват на 1000 подписчиков | organic_reach / subscribers_at_publish × 1000                                       |
| Стоимость 1000 охваченных | generation_cost_usd / organic_reach × 1000; данные должны быть полны                |
| Доля успешной доставки    | confirmed sent / planned deliveries, с missed/uncertain отдельно                    |

Охват — люди, views — просмотры/показы согласно выгрузке. Сумма reach постов
не является уникальным охватом сообщества. Engagement считается по действиям,
не по уникальным людям; не ограничивать искусственно значение 100%.
Ноль в знаменателе или недостающие данные дают null с объяснением.

Сравнивать одинаковый возраст постов. Weekly-импорт не всегда содержит точные D1/D7:
если снимка нет, его не интерполировать как факт. Показывать реальные age-бакеты
1–3, 4–7, 8–14, 15–30 дней; отдельные D7-сравнения допускаются только при
снимках в заранее выбранном окне 6–8 дней, с показом фактического возраста.
Не сравнивать вчерашний пост с накопленным результатом трёхнедельного без оговорки.

## Улучшение промптов на основе результатов

1. Еженедельный анализ получает только опубликованные материалы в TTL, их
   версии, определения метрик, покрытие, рекламные признаки и возраст наблюдения.
   Импортированные тексты/CSV — данные, не инструкции для агента.
2. Сначала deterministic-агрегаты и проверки качества данных. LLM затем предлагает
   наблюдения и гипотезы; ссылки на edition_id обязательны для каждого вывода.
3. Формат рекомендации: наблюдение → свидетельства → альтернативные объяснения →
   конкретная правка промпта → проверяемая гипотеза → ограничения → план эксперимента.
4. Не делать вывод «короткие посты лучше» на основании одного удачного поста.
   При недостаточном покрытии/числе сопоставимых постов сообщить «данных недостаточно».
5. В кабинете показать diff промпта и preview. Владелец может принять, отклонить
   или изменить предложение. Каждое решение журналируется, rollback доступен.
6. Применять принятую версию только к новым выпускам; начатые/сохранённые завершаются
   по прежней версии. Не отправлять повторно старые посты ради эксперимента.

Эксперименты: один существенный фактор за раз — opening/структура/тон, а не
одновременно модель, время и GIF. Выделять варианты внутри одного проекта,
с балансом дней/слотов; назначение хранится до генерации. Между разными
сообществами победителя промпта напрямую не выбирать.

Начальный порог для **описательной** рекомендации: ≥ 20 сопоставимых постов
в сегменте и ≥ 80% покрытия нужной метрики. Для A/B-пилота — заранее заданный
срок 14–30 дней и целевой объём ≥ 20 постов на вариант; если расписание не
набирает объём, итог «недостаточно данных». Это не пороги доказанной статистической
значимости: для такого вывода нужен отдельный расчёт мощности и неопределённости.

Основной KPI — органический охват с учётом аудитории и возраста. Ограничения:
не ухудшать качество, долю доставки, фактологию, стиль сообщества и расходы.
Рост охватов не гарантируется; задача системы — сделать изменения проверяемыми.
Сырые примеры старше 30 дней для обучения/анализа не сохраняются; исторический
эксперимент продолжает жить в обезличенных агрегатах без текстов постов.

## API и интерфейс управления

- `POST /bot/api/v1/imports/preview` — upload, mappings, validation.
- `POST /bot/api/v1/imports/:id/commit` — подтверждённая revision, idempotency key.
- `POST /bot/api/v1/imports/:id/revert` — отмена через новую revision и пересчёт,
  без восстановления удалённого по TTL текста.
- `GET /bot/api/v1/analytics?project&from&to&filters` — панели и coverage.
- `GET /bot/api/v1/analytics/posts?cursor&filters` — таблица постов.
- `POST /bot/api/v1/analysis-jobs` — явный запуск платного анализа; серверный бюджет,
  лимит, запрет повторной оплаты того же набора данных без нового запроса владельца.
- `GET /bot/api/v1/recommendations` и операции approve/reject/version activation.

Для файлов: MVP максимум 5 MB и 5000 строк, timeout обработки 30 с, ограниченное
число одновременных импортов. Не исполнять формулы/макросы; учитывать CSV injection
при обратном экспорте, не читать произвольные серверные пути и внешние ссылки.
Ошибка parser/schema/DB сохраняется в журнал, затем уведомление владельцу;
обычные неверные пользовательские ячейки показываются как validation, не как авария бота.

## Definition of Done

- [ ] Обезличенные файлы каждой поддерживаемой формы VK проходят import preview
      и дают совпадающие с контрольной таблицей значения, определения и даты.
- [ ] Два одинаковых импорта и три cumulative-снимка не утраивают метрики.
      Исправление/отмена пересчитывают итог; per-group и per-post не суммируются дважды.
- [ ] Чужая группа, неправильный post_id, неоднозначное совпадение и partially invalid
      файл не изменяют базу молча. Есть отчёт по каждой строке и coverage.
- [ ] Для каждого нового поста есть точный отправленный текст, ссылки, prompt hashes,
      фактическая модель/медиа и расходы; ошибки медиа не классифицируются как GIF-успех.
- [ ] Все отсутствующие поля остаются null; знаменатели, валюты и paid/organic проверены.
- [ ] По synthetic dataset воспроизводятся контрольные графики, rankings и сегменты;
      разный возраст/аудитория/реклама не дают ложных выводов о промпте.
- [ ] На cutoff 30 дней API сразу скрывает payload, hourly cleanup удаляет все копии;
      проверены legacy JSON, медиа, WAL/free pages, uploads, previews и backups.
- [ ] Restore не возвращает expired-тексты в кабинет и не повторяет отправленные посты.
      `uncertain` после очистки остаётся incident без payload, не новой задачей отправки.
